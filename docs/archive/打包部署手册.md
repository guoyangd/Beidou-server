# BeiDou 打包部署手册

> 适用环境：Mac（开发/打包）+ QNAP NAS（运行）。
> 本文沉淀了 2026-09 期间踩过的全部坑，每条流程都经过实际验证。
> 配套文件：仓库根目录 `build.sh`（一键打包脚本）、`docs/家用服务器docker-compose.yml`、`docs/backup.sh`。

---

## 一、总览：从代码到玩家进游戏

```
Mac 本机                          QNAP 服务器
─────────                         ─────────────────────────────────────
./build.sh                    →   File Station 覆盖上传 BeiDou.jar
（构建+自动核验+输出SHA）           Container Station 重启游戏容器
                                  （新迁移会自动执行）→ 日志确认"启动完成"
```

**核心原则（都是血泪教训）**：

1. **永远不部署未核验的 jar**——jar 里缺 UI 会表现成后台打不开且报 `40001 当前请求方法不支持`（其实是 404 被全局异常处理器包装的）；
2. **部署带新数据库迁移的 jar 前，先做一次备份**；
3. **数据和 compose 分离**——数据在 `/share/Data/docker/maplestory/`，Container Station 的应用目录会被重新部署清空，放里面等于自杀。

## 三、日常打包（改了 Java 代码后）

```bash
cd /Users/enoch/GameProject/BeiDou-Server
./build.sh
```

脚本会自动：构建 → **核验四要素**（UI 入口 / application.yml / 迁移脚本数量 / HostIpCache）→ 输出产物大小和 SHA。核验失败会自动重试 3 次（VS Code 的 Java 插件会和 Maven 抢 `target/` 目录导致随机丢资源，重试即可绕过；屡败就等 VS Code 右下角进度条跑完再打）。

**产物**：`gms-server/target/BeiDou.jar`，记住 SHA 前 16 位用于上传后核对。

> 怀疑有陈旧类编译异常时用 `./build.sh --clean` 深度清理（VS Code 开着时可能因文件锁失败，失败就重跑）。
> 手工打包命令等价于：`mvn -pl gms-server package -DskipTests`，但**必须**手动核验上述四要素再部署。

## 四、什么时候要重建管理后台 UI

只有改了 `gms-ui/` 里的前端代码才需要（后端改动不需要）：

```bash
cd gms-ui
npx -y yarn@1.22.22 install --registry https://registry.npmmirror.com   # 依赖没变可跳过
npx -y yarn@1.22.22 build                                               # 约 8 分钟
cp -R dist/. ../gms-server/src/main/resources/static/
cd .. && ./build.sh
```

## 五、部署到 QNAP（日常换 jar）

1. **备份**：Container Station 重启 `beidou-db-backup` 容器（启动即备一份最新），或等最近的定时备份（每天 01:00/09:00/15:00/21:00）；
2. **上传**：File Station 覆盖 `/share/Data/docker/maplestory/beidou-server-release/BeiDou.jar`（建议先把旧 jar 改名为 `BeiDou.jar.bak` 留回滚）；
3. **核对**：File Station 里看文件大小与 Mac 侧一致（Mac 侧 `ls -lh` 对比；QNAP 无命令行时大小是快速核对手段）；
4. **重启**：Container Station 重启 `beidou-server-all`；
5. **验证**：容器日志出现 `北斗 启动完成`；浏览器进后台能登录；游戏客户端进一次。健康检查变 healthy 即代表游戏端口就绪。

**回滚**：把 `BeiDou.jar.bak` 改回原名、重启容器。注意：若新 jar 已执行过**新的** Flyway 迁移，旧 jar 可能不认识新表结构——所以第 1 步的备份不是仪式。

## 六、带数据库迁移的部署（额外注意）

新 jar 里如果多了 `V1.x.x__*.sql`（对比 `git log --stat` 或构建日志），首次启动会自动改表。流程与第五节相同，但：

- 务必先做第 1 步备份；
- 启动日志中确认出现 `Migrating schema beidou to version V1.x.x` 且无异常；
- 万一迁移中断导致后续启动报 Flyway 错误，恢复备份：
  ```bash
  gunzip < /share/Data/docker/maplestory/docker-db-backup/最新备份.sql.gz | \
      docker exec -i beidou-db mysql -uroot -p'密码' beidou
  ```

## 八、常见问题对照表（按症状查）

| 症状 | 原因 | 处理 |
|---|---|---|
| `./build.sh` 三次核验失败 | VS Code Java 插件抢占 target/ | 等它索引完重跑；或关 VS Code |
| 构建产物 jar 明显偏小（108M vs 113M） | 资源没拷进去（同上竞态） | 用 build.sh 重打，勿手工部署 |
| 后台打不开，页面/接口返回 `40001 当前请求方法不支持` | **jar 里没有 UI**（static/ 缺失） | 用 build.sh 核验通过的 jar；缺 UI 时重新执行第四节拷贝 dist |
| docker logs 每行两份 | stdout 和 logs/out.log 被合到一处看 | 给容器加环境变量 `LOG_FILE_LEVEL=OFF`（只留 docker logs）或 `LOG_CONSOLE_LEVEL=OFF`（只留文件） |
| 停机时刷 `Unable to unregister MBeans` | log4j2 JMX 清理碰已销毁的 Undertow 上下文 | 新 jar 已修（log4j2.component.properties）；仅旧 jar 出现 |
| 日志每 30 秒一条 `客户端 127.0.0.1 连接到了登陆端口` | 旧 jar 无回环静默 + compose 健康检查探 8484 | 换 2026-09-09 之后的 jar |
| 玩家登录前反复失败，日志见 `域名 xxx 解析失败/解析到无效地址` | DDNS 记录异常（私网污染/双IP互搏） | 查路由器与 QNAP 是否双 DDNS 更新源；DNS 控制台删多余 A 记录。服务端已自带缓存+拒收脏地址+变更确认 |
| 启动失败 `自动创建数据库失败：CommunicationsException` | MySQL 未就绪竞态 | compose 的 db 健康检查已改 TCP 探测；旧 compose 会偶发，重启游戏容器即可 |
| Container Station 重新部署后数据没了 | 数据放在了应用目录（会被清空） | 数据必须在 `/share/Data/docker/maplestory/`（绝对路径挂载），见第七节 |

## 九、日志导出（排障用）

- 容器日志：`docker logs`（无命令行时看 Container Station 容器日志页）；重要日志及时导出——**容器重建后 docker logs 会清零**；
- 域名健康：搜 `HostIpCache` 关键字（解析成功/变更/失败/无效地址/恢复）；
- 登录失败：搜 `登录失败`（账号+IP+错误码，常见：4 密码错 / 5 账号不存在 / 7 已登录 / 17 多开占用）。
